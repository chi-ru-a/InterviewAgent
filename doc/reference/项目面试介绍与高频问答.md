# cmint AI 闯关学习小程序：项目面试介绍与高频问答

> 这份文档按当前仓库实现整理，目标不是让你背技术名词，而是帮助你在面试中清楚回答四件事：
>
> 1. 这个项目解决了什么问题；
> 2. 用户和数据是怎样流转的；
> 3. 你为什么这样设计、实际做了什么；
> 4. 当前方案有什么边界，下一步如何演进。

## 1. 项目介绍的通用套路

面试官通常不是只想听“用了哪些框架”，而是想判断你是否真正理解简历上的项目，以及你的经验能否迁移到岗位。哈佛大学就业服务中心的面试建议也强调：要熟悉简历上的每一项经历，能够解释“做了什么”和“为什么这样做”，并把经历和目标岗位联系起来，同时通过练习提升表达的清晰度。

因此，建议采用下面这条主线，而不是按文件目录逐个念：

```text
项目定位
  -> 业务痛点
  -> 核心用户流程
  -> 系统架构与数据流
  -> 我的具体贡献
  -> 一个关键技术难点
  -> 结果与当前边界
  -> 下一步优化
```

### 1.1 90 秒项目介绍模板

可以按下面 7 句话组织。每句话回答一个问题：

1. **是什么**：这是一个面向什么用户的什么系统。
2. **为什么做**：原来的学习或业务流程有什么问题。
3. **怎么做**：系统的核心链路是什么。
4. **技术方案**：前后端、存储、AI/RAG 分别承担什么职责。
5. **我做了什么**：明确说个人负责的模块，不要只说“我们”。
6. **难点和取舍**：遇到什么问题，为什么选择当前方案。
7. **结果和边界**：当前完成了什么，哪些是 MVP 的限制，下一步怎么改。

### 1.2 回答技术追问的 STAR 变体

技术项目不必机械地讲传统 STAR，可以使用：

| 环节 | 要回答的问题 | 本项目中的例子 |
| --- | --- | --- |
| S：场景 | 用户或系统当时遇到什么问题？ | 用户有学习主题，但缺少即时练习和复盘 |
| T：目标 | 需要达到什么效果？ | 从输入主题到生成题库、答题、报告形成闭环 |
| A：行动 | 你具体如何设计和实现？ | 任务轮询、RAG 检索、结构化输出校验、历史持久化 |
| R：结果 | 最终带来什么结果？ | 支持主题出题、联网增强、私有文档出题、报告和历史回看 |
| L：Lesson | 你学到什么、还会怎么改？ | 进程内任务适合 MVP，生产环境应迁移到持久化队列 |

如果没有真实线上指标，不要编造“性能提升 80%”或“用户增长 3 倍”。可以诚实描述**功能结果、数据边界和后续指标**。

## 2. 这个项目的一句话定位

> **cmint AI 是一个微信小程序形态的 AI 闯关学习工具：用户输入想学习的主题，系统通过联网搜索或用户私有知识库补充上下文，由大模型生成结构化题库，用户逐题作答后获得即时解析和复盘报告，并可以保存历史、生成分享海报。**

简历上可以概括为：

> **基于 Taro + React、FastAPI、DeepSeek、LangChain、Chroma 和 MySQL 实现 AI 闯关学习闭环，支持联网增强出题、私有文档 RAG、异步任务、结构化题库校验、答题复盘与历史回看。**

## 3. 可直接口述的 90 秒版本

> 我做的是一个微信小程序形态的 AI 闯关学习工具，主要解决用户知道自己想学什么，但很难快速获得针对性练习和复盘的问题。用户在首页输入一个主题，比如 RAG 或数据库，系统会先判断当前用户是否有可用的私有知识库：如果有，就通过 Chroma 做向量检索；如果没有或资料不足，就通过 Tavily 做联网搜索。检索结果会被整理成上下文，再交给 DeepSeek 生成结构化题库。
>
> 题库生成可能包含搜索、大模型和可选生图，耗时不稳定，所以我没有让前端一直等待一个同步请求，而是由接口先返回 `task_id`，后台执行任务，前端轮询状态。模型返回的数据经过 Pydantic 校验和归一化，保证题型、选项和答案之间是一致的。用户答题时前端立即完成评分并展示解析，最后把题库和答题记录交给报告生成模块，生成掌握点、薄弱点和学习建议，并保存到 MySQL，之后可以在历史记录中回看。
>
> 技术上前端使用 Taro + React，后端使用 FastAPI，业务数据放 MySQL，文档向量放 Chroma，模型能力通过 LangChain 统一接入。这里我比较关注两个问题：一是大模型输出不稳定，所以做了结构化校验和容错；二是知识库必须按用户隔离，检索时同时使用用户和文档元数据过滤。当前方案是单进程 MVP，出题任务保存在内存中，生产环境我会把它迁移到 Redis 加持久化任务队列，并补充可观测性和更严格的权限控制。

## 4. 按模块介绍业务流

### 4.1 用户登录流

1. 小程序调用 `Taro.login()` 获取微信临时 `code`。
2. 后端向微信换取 `openid`。
3. 后端按 `openid` 查询用户，不存在则创建用户。
4. 后端签发 JWT，前端保存 `authToken` 和用户信息。
5. 后续请求通过 `Authorization` 传递 JWT。
6. 需要登录的接口从 JWT 中得到 `user_id`，用于访问用户资料、历史和知识库。

这里要强调：JWT 当前主要解决“用户是谁”，没有做角色系统；匿名主题出题可以返回结果，但匿名结果不会进入用户历史。

### 4.2 主题出题流

```text
用户输入主题
  -> POST /api/v1/quiz/generate
  -> 返回 task_id
  -> 后台执行检索、出题、可选配图、持久化
  -> 前端每 3 秒查询任务状态
  -> succeeded 后进入答题页
```

检索策略如下：

```text
指定 doc_id
  -> 校验文档属于当前用户且状态为 ready
  -> 在指定文档范围内做 Agentic RAG

未指定 doc_id，但用户有 ready 文档
  -> 在该用户自己的文档集合中检索

没有可用私有文档
  -> 使用 Tavily 联网搜索
```

RAG 或联网搜索得到的是“参考上下文”，并不是直接返回给用户的最终题目。上下文会进入出题 Prompt，DeepSeek 再生成题库。

### 4.3 文档知识库流

```text
上传 PDF/DOCX/MD/TXT
  -> 校验扩展名、大小、数量和空文件
  -> 保存原文件和 processing 元数据
  -> 后台 Loader 解析
  -> RecursiveCharacterTextSplitter 分块
  -> Embedding
  -> 写入用户专属 Chroma collection
  -> 更新文档状态为 ready
```

知识库的隔离有三层：

1. MySQL 的 `kb_documents` 记录 `user_id`；
2. Chroma collection 按用户划分，例如 `kb_user_{user_id}`；
3. 每个向量 chunk 的 metadata 同时保存 `user_id` 和 `doc_id`，检索和删除都带过滤条件。

因此，面试时不要只说“用了向量数据库”，要能说清楚**数据如何进入向量库，以及如何防止跨用户检索**。

### 4.4 答题和复盘流

1. 前端从 `currentQuiz` 读取题目。
2. 用户提交答案后，前端比较答案集合；多选题要求集合完全一致。
3. 页面立即展示对错、解析和知识点。
4. 每题记录 `question_id`、`selected_answers`、`duration_ms`。
5. 最后一题完成后请求报告接口。
6. 后端计算总题数、已答数、正确数和正确率。
7. 报告模型生成评价、掌握点、薄弱点、总结和建议。
8. 登录用户将题库、答题记录和报告保存到 MySQL。
9. 前端展示报告，并支持从历史记录重新查看或生成分享海报。

## 5. 系统架构和数据流

### 5.1 分层职责

| 层次 | 技术 | 主要职责 |
| --- | --- | --- |
| 客户端 | Taro + React | 页面、登录态、任务轮询、答题交互、本地临时状态 |
| API 层 | FastAPI | 路由、Pydantic 请求校验、JWT 依赖、统一响应和异常 |
| 业务层 | quiz task、RAG、搜索、评分、配图 | 编排跨模块业务流程 |
| AI 层 | DeepSeek、Tavily、百炼 Embedding/生图 | 出题、报告、搜索、向量化和图片生成 |
| 持久化层 | MySQL、Chroma、本地文件、COS | 用户和历史、向量、上传文件、图片 |

### 5.2 一次闯关的数据生命周期

```text
输入主题
  -> FastAPI 请求模型
  -> task_id（任务状态在进程内）
  -> RAG/联网搜索
  -> search_context
  -> DeepSeek
  -> Quiz JSON
  -> Pydantic Quiz 校验
  -> 可选生图并上传 COS
  -> quiz_sessions
  -> 前端答题
  -> AnswerRecord
  -> calculate_score
  -> DeepSeek Report
  -> answer_records + reports
```

主要数据对象及去向：

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| `QuizTask` | `task_id`、`status`、`quiz`、`error` | 前端轮询异步出题 |
| `Quiz` | `quiz_id`、题目列表、`search_used` | 答题和历史回看 |
| `Question` | 题型、选项、答案、解析、知识点 | 展示、评分和报告 |
| `AnswerRecord` | 题目 ID、选择结果、耗时 | 评分和学习行为记录 |
| `Report` | 正确率、掌握点、薄弱点、建议 | 复盘和分享 |
| `KnowledgeDocument` | `doc_id`、状态、`chunk_count` | 知识库管理 |
| 向量 chunk | 文本和用户/文档 metadata | 相似度检索 |

## 6. 面试中最值得展开的技术点

### 6.1 为什么出题做成异步任务加轮询？

出题不是单次快速数据库查询，可能依次包含联网搜索、网页提取、模型生成和多题生图，耗时具有不确定性。同步接口容易超时，也会占住 HTTP 连接。

当前实现是：

```text
POST 创建任务 -> 立即返回 task_id
后台 asyncio.create_task 执行
前端 GET task_id 查询 pending/running/succeeded/failed
```

这是适合当前单进程 MVP 的低成本方案。它的边界是任务状态只在内存中，服务重启会丢失，且多实例部署时不同实例之间看不到同一任务。生产改造应使用 Redis 保存状态，并用 Celery、RQ 或云任务队列执行，配合重试、超时、死信和任务幂等。

### 6.2 如何处理大模型输出不稳定？

不能把模型返回的字符串直接交给前端。当前链路是：

1. Prompt 要求返回 JSON；
2. 使用模型的 JSON response format；
3. `parse_json_response` 处理字符串、字典或多模态内容；
4. Pydantic `Quiz`、`Question`、`Option` 做领域校验；
5. 对中文题型、难度、字段别名和答案字符串做归一化；
6. 校验答案必须引用真实选项；
7. 判断题缺少选项时补齐“正确/错误”。

校验失败不能静默返回一个看似成功的空题库，应将任务标记为失败并记录日志，前端展示可理解的错误。

### 6.3 Agent、RAG 和普通 Prompt 的关系是什么？

三者不是同一层概念：

- **Prompt**：告诉模型如何生成题目或报告；
- **RAG**：先检索外部知识，再把相关内容作为上下文交给模型；
- **Agent**：模型根据任务选择调用搜索、网页提取或知识库检索工具。

本项目中，Agent 负责决定是否调用工具，工具负责获取资料，最终得到的文本摘要统一放入出题 Prompt。这样出题模型不需要关心资料来自 Tavily 还是 Chroma。

当前项目通过 `create_agent` 间接使用框架提供的执行图，没有手写 `StateGraph`。面试时应该准确表达为“使用 LangChain 的 Agent 能力，底层由 LangGraph 提供执行机制”，不要说成自己实现了完整的 LangGraph 状态图。

### 6.4 如何保证用户知识库隔离？

授权不能只在文件上传接口校验一次。读取、检索、删除都要重复校验：

- SQL 查询带 `user_id`；
- 指定文档时校验 `doc_id + user_id`；
- Chroma collection 按用户隔离；
- metadata 保存 `user_id` 和 `doc_id`；
- 相似度检索和删除带 metadata 过滤。

这属于业务层和数据层同时做边界控制，避免只依赖前端传来的 `doc_id`。

### 6.5 为什么要做降级？

搜索服务、Embedding、模型、生图都属于外部依赖，任何一个失败都不应该让不相关的核心能力全部不可用。例如：

- 搜索失败：使用用户原始主题继续出题；
- RAG 失败：退回联网搜索或无上下文出题；
- 单题生图失败：返回无图题库并提示；
- 海报文案失败：使用报告金句和成绩生成备用文案。

降级的原则是：**保留核心学习闭环，同时明确告知用户增强能力没有生效**，不能把失败伪装成成功。

## 7. 高频面试问题与参考回答

### Q1：你在这个项目中具体负责什么？

> 我主要负责从主题输入到题库生成、答题复盘和历史回看的核心链路，同时实现了联网搜索增强和用户私有知识库 RAG。具体包括 FastAPI 接口和业务编排、异步出题任务、模型输出的 Pydantic 校验、文档解析分块与 Chroma 检索、MySQL 历史持久化，以及前端轮询和答题状态管理。除了功能实现，我也明确了当前 MVP 的边界，例如任务状态仍在进程内，生产环境需要迁移到持久化队列。

### Q2：为什么选择 RAG，而不是直接让大模型出题？

> 直接出题容易出现知识过时、事实不准确和无法基于用户资料出题的问题。RAG 先从用户私有文档中召回相关片段，再把片段作为参考上下文交给模型，能让题目更贴近用户正在学习的材料。没有私有资料时再使用联网搜索，搜索失败时退回原始主题，保证系统仍能完成基本出题。

### Q3：向量检索具体是怎么做的？

> 上传文档后先按文件类型选择 Loader，再用递归字符切分器分块，调用 Embedding 模型把文本转成向量，最后写入 Chroma。检索时把用户问题向量化，执行相似度搜索，并用 `user_id`、可选的 `doc_id` 过滤。召回文本会整理成上下文，交给 Agent 或出题模型使用。

### Q4：为什么不用同步接口直接返回题库？

> 因为一次生成可能包含搜索、模型调用和多张图片生成，耗时和失败点较多。同步请求会增加超时风险，所以我把它拆成“创建任务”和“查询任务状态”两个接口。前端轮询虽然实现简单，但当前只适合单进程 MVP；如果扩展到多实例，我会把状态放到 Redis，并使用持久化任务队列。

### Q5：大模型返回非法 JSON 或字段缺失时怎么办？

> 先通过 Prompt 和 JSON response format 降低概率，再在服务端进行解析和 Pydantic 校验。模型可能返回中文字段、字符串答案、缺少题型或判断题选项，因此模型层做字段别名、类型归一化和合理补全。但答案必须最终映射到真实选项，无法满足领域约束就让任务失败，而不是返回错误题库。

### Q6：多选题如何评分？

> 前端把用户选择和标准答案都当作集合比较，只有集合完全一致才算正确，避免“选中部分正确答案”被误判为正确。答题记录仍会保存选择结果和耗时，后端报告生成时使用统一的评分结果。

### Q7：为什么不把答案评分完全放在后端？

> 当前产品需要点击提交后即时反馈，所以前端本地评分可以减少一次网络往返，交互更快。但前端结果不能作为安全或计费依据；如果要做可信成绩、排行榜或考试场景，我会把题库版本和评分规则放在后端，后端重新计算并以服务端结果为准。

### Q8：项目中的 MySQL 和 Chroma 分别存什么？

> MySQL 存结构化业务数据，例如用户、闯关会话、答题记录、报告和知识库文档元数据；Chroma 存文档切分后的向量和 metadata，用于相似度检索。原始上传文件放文件存储，题目图片上传到 COS。这样把事务型数据和向量检索数据分开，各自使用合适的存储方式。

### Q9：如何避免重复生成报告或重复增加 XP？

> 报告生成接口需要按 `quiz_id` 做幂等处理：已存在报告时优先复用或更新，而不是重复插入；XP 只能在首次完成时增加。生产环境还需要数据库唯一约束、事务和并发控制，避免多个请求同时判断“尚未生成”后重复累加。

### Q10：当前项目最大的技术债是什么？

> 最大的技术债是异步任务仍在进程内内存中，服务重启会丢任务，多实例也无法共享状态。其次是外部模型和搜索调用还可以补充更细的耗时、token、错误率监控。下一步会将任务迁移到 Redis 加持久化队列，增加重试和幂等键，并补充 tracing、指标和告警。

### Q11：如果用户上传一个很大的 PDF，会有什么问题？

> 可能出现解析耗时长、Embedding 请求过大、内存占用高和任务阻塞。当前通过上传限制、切块和后台处理降低风险。进一步会增加页数和总文本长度限制、分批 Embedding、任务进度、超时与取消机制，并对重复文件做 hash 去重。

### Q12：如何评估题目质量，而不仅是“接口返回成功”？

> 可以分三层评估：第一层是结构校验，例如答案必须存在于选项；第二层是事实一致性，抽样检查题目是否能被检索上下文支持；第三层是用户效果，例如答题正确率、题目纠错率、报告采纳率和失败重试率。上线前可以构造固定主题和参考答案做回归集，比较不同 Prompt 或模型版本。

### Q13：为什么没有直接手写 LangGraph？

> 当前需求主要是有限工具调用的检索 Agent，不需要复杂的状态节点、人工审批或长流程恢复，因此使用 `create_agent` 足够，开发成本更低。LangGraph 在底层提供了执行图能力。如果未来加入多阶段检索、质量审核、人工确认、可恢复中断，我会再显式设计 StateGraph 和持久化 checkpoint。

### Q14：如果让你把这个项目上线，你会优先改什么？

> 我会按风险优先级改四件事：第一，把进程内任务迁移到 Redis 和持久化队列；第二，收紧 CORS、密钥管理、文件访问和上传内容校验；第三，为模型、搜索、Embedding 和生图增加超时、重试、熔断、日志和指标；第四，增加题目质量回归集与端到端测试。这样先解决可靠性和安全边界，再做更复杂的学习推荐功能。

## 8. 面试时不要这样说

| 不推荐说法 | 更准确的说法 |
| --- | --- |
| “我实现了一个完整的 LangGraph 工作流” | “我使用 LangChain Agent，底层执行机制由 LangGraph 提供，当前没有手写 StateGraph” |
| “系统用了消息队列” | “当前是 `asyncio.create_task` 的进程内任务；生产环境计划迁移到持久化队列” |
| “大模型保证生成内容完全正确” | “通过检索上下文、结构化校验和质量回归降低错误，但不能宣称完全正确” |
| “前端算分所以成绩可信” | “前端负责即时反馈；可信成绩场景需要后端重新评分” |
| “用了向量库所以天然安全” | “通过 SQL 用户归属、用户 collection 和 metadata 过滤共同实现隔离” |
| “项目已经支持所有规划功能” | “当前闭环是出题、答题、报告、历史和知识库，PK、遗忘曲线等仍是规划” |

## 9. 反问面试官的问题

当面试官问“你还有什么想了解的吗”，可以选择与岗位相关的问题：

1. 这个岗位更看重业务功能交付，还是平台稳定性和工程治理？
2. 团队目前使用什么方式处理异步任务、模型调用和可观测性？
3. AI 功能上线后，团队主要用哪些指标评估质量和成本？
4. 如果加入团队，入职前三个月最希望我解决哪类问题？

## 10. 你需要提前准备的真实信息

文档中的技术链路来自代码，但面试中的“我负责”和“项目结果”必须替换成你自己的真实经历。面试前补齐下面内容：

- 项目开发周期、参与人数和你的职责边界；
- 是否实际部署过，部署环境和访问方式；
- 是否有真实用户或测试数据；
- 你亲自解决过的一个具体 Bug；
- 你做过的性能、稳定性或成本优化；
- 一次失败方案和最终为什么放弃；
- 如果简历写了指标，准备好指标的统计口径和时间范围。
